    7. 第 6 章 - 结论与后续步骤

    7.1. 已构建的内容

    本文档把 [RdvMedecins] 应用的功能核心 和 身份验证从 2014 年的原文档改编到了当前技术上：

    • 一个完整的 [NestJS] 服务器（[TypeORM] 实体、DAO、业务层、Web 层），在同一端口（8080）上公开与原 Spring 4 服务器相同的 11 个业务路由（JSON），现在全部由令牌（JWT）保护；
    • 一个 身份验证层（[@nestjs/passport] + [@nestjs/jwt]）：登录名/密码身份验证（POST /login）、随每个后续请求提交的已签名令牌，以及在两个修改数据的路由上基于角色的访问控制（[@Roles]('ADMIN') + [RolesGuard]）；
    • 一个 [React] 客户端（函数组件、Hook），提供与原 AngularJS 1.x 客户端相同的功能——选择医生和日期、查看日程表、预约和取消预约——并增加了登录界面、持久会话（localStorage）、根据已登录用户的角色进行调整的 Bootstrap 界面（对特定角色隐藏预约按钮），以及在法语和英语之间切换界面的能力（[i18next] + [react-i18next]）。

    数据库的核心没有改变（相同的表 [doctors/clients/slots/appointments]，相同的约束），只是增加了表 [users]；总体的分层架构也没有改变——更新的只是实现它的工具。

    与原文档的身份验证方式有两处有意的差异，已在第 3 章中详细说明：使用 JWT 令牌，而不是每次请求都发送 HTTP Basic 请求头；以及每个用户使用单个 [role] 列，而不是跨三张表的多对多关系。第三处差异——这是功能上的差异——是本次移植有意选择的：角色 USER 现在可以查看日程表（只读），而在原文档中它只用来演示完全拒绝访问。

    7.2. 不在范围内或有待移植的内容

    除上述内容之外，原文档还涵盖另外三个主题——其中一个现已解决，另一个被有意排除，第三个推迟到后续阶段：

    7.2.1. 法语/英语本地化——本文档已解决

    原文档提出使用 [angular-translate] 库在法语和英语之间切换界面。本次移植使用当前 [React] 生态中的对应工具 [i18next] （连同 [react-i18next]，它通过 HTTP 从 [public/i18n/] 文件夹加载字典 fr.json/en.json）实现了这一功能——见第 5 章。与此前的 [angular-translate] 一样，[i18next] 允许您即时切换语言，而无需重新加载页面——这一行为忠实于原文档。

    7.2.2. 客户端的“调试”模式——有意排除在范围之外

    原文档包含一个可从界面激活的技术显示模式，它可以访问当前视图的原始模型（AngularJS 1.x 的 $scope）——这在 2014 年是一个有用的功能，当时可用于检查 AngularJS 应用的开发工具还很有限。本次移植没有重现它：当前的 [React] 开发工具（[React] DevTools，官方浏览器扩展）现在可以在应用之外，对组件、它们的状态（Hook）和 props 提供比重新集成到界面中的自定义调试面板全面得多的检查。添加这样的面板，无异于创建一个已由生态提供的工具的简化版本——因此这一决定是最终的，而不仅仅是推迟。

    7.2.3. 人为网络延迟——推迟

    原文档允许在每次服务器响应之前设置人为延迟，以观察界面在慢速网络下的行为（加载指示器、临时禁用按钮等）。本次移植中尚没有与此功能对应的实现。

    7.3. 关于本文档所采用方法的说明

    本文档完全基于实际执行过的代码编写：每条服务器路径都经过测试（包括身份验证场景：登录成功/失败、不带令牌访问、使用错误角色访问），第 5 章中的每张客户端截图都是通过与实际运行的应用交互获得的——使用由程序自动控制的 Chromium 浏览器，数据来自所提供 SQL 脚本中的演示数据。这种方法还在准备本文档期间发现了一个关于 [TypeORM] 与计算列（[@RelationId]）一起使用的具体问题——该问题已在第 3 章中报告并修正，直接体现在交付的代码中。这一要求也解释了为什么本文档不包含 Postman 截图：与其模拟它们，似乎更好的做法是把这一步留给文档作者，他可以直接在自己的工作站上创建它们。

    7.4. 立即上手

    在等待本次移植的后续步骤期间，本文档附带的服务器和客户端为您提供了一个现成可用的基础，供您自行试验：

    • 添加新的医生或新的患者（目前只能通过修改 SQL 脚本来完成——一个名为 /addDoctor 的路由，同样受 [@Roles]('ADMIN') 保护，可以作为一个很好的第一个练习）；
    • 添加第三个角色，或拥有多个角色的用户——借此机会以非常具体的方式评估放弃单列简化方案 [role] 的代价（见第 3 章）；
    • 修改客户端的呈现（颜色、布局）而不改动服务器——这是验证客户端分层架构按预期工作的好办法；
    • 查阅所交付的服务器和客户端中每个文件夹的 README 文件：每个文件都在其上下文中解释了其所含文件的作用。
