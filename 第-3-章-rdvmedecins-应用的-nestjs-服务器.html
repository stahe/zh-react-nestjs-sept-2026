    • 第 20–24 行：[DROP TABLE IF EXISTS …] ——脚本每次执行都从空数据库开始，并按依赖关系的相反顺序删除（先是引用 `[slots]` 和 `clients` 的 `appointments`，一直到不被任何表引用的 `users`）：[MySQL] 会拒绝删除仍被外键引用的表；
    • 第 48 行：[doctor_id INT NOT NULL]，然后是第 53 行：[CONSTRAINT fk_slots_doctor FOREIGN KEY …] ——时间段始终属于某位医生；
    • 第 64 行：[CONSTRAINT unq1_appointments UNIQUE (day, slot_id)] ——应用的核心业务规则：同一天的同一个时间段只能被预约一次。防止重复预约的正是这个约束，而且仅靠这个约束——验证器和业务逻辑层都不会显式地再次检查它（见下文的 addAppointment）；
    • 第 67–74 行：[CREATE TABLE users (…)] ——本步骤新增的表。`login` 是 UNIQUE 的（两个用户不能使用相同的登录 ID）；`password` 存储的是使用 bcrypt 哈希后的密码（绝不存明文）；role 取值为 'ADMIN' 或 'USER'——一个简单的文本列，而原文档使用三张表（users、roles、users_roles）来允许每个用户拥有多个角色。由于本应用只需要两个互斥的角色，原来的多对多关系就显得多余了；
    • 第 91–93 行：[INSERT INTO users …] ——两个演示账户，admin/admin（角色 ADMIN）和 user/user（角色 USER），其密码已用 bcrypt 哈希（加盐 10 轮）——绝不存明文，在这个演示脚本中也是如此。

      import { [PrimaryGeneratedColumn], [VersionColumn] } from 'typeorm';

  export abstract class AbstractEntity {
    @PrimaryGeneratedColumn()
    id: number;

    @VersionColumn()
    version: number;
  }

    我们来解读这段代码：

    • 第 4 行：[@PrimaryGeneratedColumn()] ——声明由 DBMS 自动递增的主键——完全等价于 JPA 中的 @Id + @GeneratedValue(strategy = GenerationType.AUTO)；
    • 第 7 行：[@VersionColumn()] ——[TypeORM] 用于 乐观锁的原生机制：[TypeORM] 在每次修改时自动递增该列，如果您尝试保存的实体其版本与数据库中的版本不再一致（其间有人修改过它），就会抛出错误——完全等价于 JPA/Hibernate 中的 @Version；
    • 第 3 行：[export abstract class AbstractEntity {] ——这个类没有用 [@Entity] 装饰：它本身不对应任何表。[TypeORM] 把这种技术称为“具体表继承”（Concrete Table Inheritance）：每个用 [@Entity] 装饰的子类都有自己的表，包含所有继承的列——完全等价于 JPA 中的 @MappedSuperclass。

      import { [Column], [Entity], [JoinColumn], [ManyToOne], [RelationId] } from 'typeorm';
  import { AbstractEntity } from './abstract.entity';
  import { Doctor } from './doctor.entity';

  @Entity({ name: 'slots' })
  export class Slot extends AbstractEntity {
    @Column({ name: 'start_hour' }) startHour: number;
    @Column({ name: 'start_minute' }) startMinute: number;
    @Column({ name: 'end_hour' }) endHour: number;
   @Column({ name: 'end_minute' }) endMinute: number;

   @ManyToOne(() => Doctor, (doctor) => doctor.slots)
   @JoinColumn({ name: 'doctor_id' })
   doctor: Doctor;

   @RelationId((slot: Slot) => slot.doctor)
   doctorId: number;
 }

    我们来解读这段代码：

    • 第 7–10 行：[@Column({ name: 'start_hour' }) startHour: number; …] ——预约时间段的四个时间边界（开始和结束的小时/分钟），四个单独的整数，各自映射到其蛇形命名的列（start_hour、start_minute、end_hour、end_minute）；
    • 第 12 行：[@ManyToOne(() => Doctor, (doctor) => doctor.slots)] ——多个时间段属于同一位医生。默认情况下，[TypeORM] 读取时间段时不会加载“doctor”关系（默认的“懒加载”行为）：必须显式请求（在查询中使用选项 relations: ['doctor']）——正如在 JPA 方面，FetchType.LAZY 要求在 JPQL 查询中显式使用 `left join fetch` 才能获取医生；
    • 第 13 行：[@JoinColumn({ name: 'doctor_id' })] ——指定表 [slots] 中外键列的名称；
    • 第 16 行：[@RelationId((slot: Slot) => slot.doctor)] ——在 [TypeORM] 方面，与原项目中只读字段 idMedecin（[@Column](name = "id_medecin", insertable = false, updatable = false)）完全对应且符合惯用法：它直接公开外键的值，无需加载整个 [Doctor] 实体——这对构建轻量的 JSON 响应很有用（见下文的 Web 层）。

    注：[@RelationId] 字段是一个 虚拟列，由 [TypeORM] 事后计算得出——它不是真正的 SQL 列，不能用于“查询构建器”的 WHERE 子句（见下文的 [SlotRepository]）。它仅用于在实体加载后 获取 外键的值。

  @Unique('unq1_appointments', ['day', 'slot'])
  export class Appointment extends AbstractEntity {
    @Column({ type: 'date' })
   day: string;

   @ManyToOne(() => Client)
   @JoinColumn({ name: 'client_id' })
   client: Client;

    4.5. DAO 层（src/repositories/）

    DAO 层（数据访问对象，Data Access Object）是项目中唯一直接与 TypeORM/MySQL 通信的部分——相当于原项目中的 Spring Data 接口（包 rdvmedecins.repositories）。

    Spring Data 与 [TypeORM] 之间最需要理解的区别：使用 Spring Data 时，只需 声明一个接口 （extends CrudRepository<...>），就能自动获得基本方法（findAll、findOne、save、delete 等）——Spring 会在启动时自行生成实现它的类。而使用 [TypeORM] 时，不会根据接口自动生成实现：我们直接注入由 [TypeORM] 提供的通用 Repository<Entity>（通过 [@InjectRepository]），并自己编写想要公开的方法，这些方法基于该 Repository 的预定义方法，或者针对更特定的查询使用 查询构建器 。

    4.8. 身份验证（src/auth/）

    本节记录在课程这一阶段加入的基于令牌的身份验证（JWT）和基于角色的访问控制（ADMIN/USER）——在功能上等价于原文档中的 Spring Security 层，使用 [NestJS] 生态中的标准工具重写：[@nestjs/passport] 和 @nestjs/jwt。

    与原项目的两个有意设置的差异，在此一次性说明：

    1. 使用 JWT 而不是 HTTP Basic。原 Spring 项目在 每个请求中都发送 Authorization: Basic <Base64 编码的 login:password> 请求头：因此密码（经过编码，而非加密）在每次调用时都会在网络上传输。本次移植改用 令牌：JWT （JSON Web Token）。密码 只提交一次，即登录时（POST /login）；服务器随后返回一个已签名的令牌，客户端在之后的每个请求中都携带它（Authorization: Bearer <token> 请求头）。这是此类 API 当前的通行做法，正如上一章的结论中已经提到的。
    2. 每个用户一个角色，数据库中的单个列，而不是原项目中的多对多关系（users/roles/users_roles）——见上文的 user.entity.ts。

    阅读后面的代码之前需要理解的一个架构要点：当守卫拒绝请求时（401 Unauthorized、403 Forbidden），响应绝不会经过通常的 [ServerResponse]<T> 信封（{ status, data }）：[NestJS] 直接以其原生 JSON 格式响应，即 { statusCode, message, error }。这是有意的选择：安全错误由守卫在进入控制器 之前 处理，而 [ServerResponse]<T> 是由 控制器针对 业务错误（资源未找到、日期无效等）生成的。因此，[React] 客户端必须区分这两类错误响应（见下一章的 auth.interceptor.ts）。

  @Injectable()

    constructor(private readonly reflector: Reflector) {}

   canActivate(context: ExecutionContext): boolean {
     const requiredRoles = this.reflector.getAllAndOverride<Role[]>(ROLES_KEY, [
       context.getHandler(),
       context.getClass(),

  import { JwtService } from '@nestjs/jwt';
  import * as bcrypt from 'bcryptjs';
  import { UserRepository } from '../repositories/user.repository';
  import { User } from '../entities/user.entity';
  import { LoginResult } from './login-result.model';
  import { JwtPayload } from './jwt.strategy';

  @Injectable()
 export class AuthService {
   constructor(
     private readonly userRepository: UserRepository,
     private readonly jwtService: JwtService,
   ) {}

   async validateUser(login: string, password: string): Promise<User | null> {
     const user = await this.userRepository.findByLogin(login);
     if (user === null) {
       return null;
     }
     const passwordCorrect = await bcrypt.compare(password, user.password);
     return passwordCorrect ? user : null;
   }

   login(user: User): LoginResult {
     const payload: JwtPayload = { sub: user.id, login: user.login, role: user.role };
     return {
       accessToken: this.jwtService.sign(payload),
       login: user.login,
       name: user.name,
       role: user.role,
     };
   }
 }

    我们来解读这段代码：

    • 第 10 行：[export class AuthService {] ——在概念上等价于原 Spring Security 项目中的 AppUserDetailsService 类，这里与令牌生成合并在一起；
    • 第 16 行：[async validateUser(login: string, password: string): Promise<User | null> {] ——验证存在使用该 login 的用户，且所提供的密码与之匹配；一切正确则返回该用户，否则返回 null；
    • 第 21 行：[const passwordCorrect = await bcrypt.compare(password, user.password);] ——bcrypt.compare() 使用相同的 盐（即存储在 user.[password] 中的盐）对密码进行哈希，然后比较两个结果——存储的密码绝不会被解密（哈希不可逆）；

    • 第 16 行：[“strictNullChecks”: true,] ——要求显式处理 null/undefined 值（使用 ?、??、if 语句……）——这是 TypeScript 严格模式的选项之一，这里单独启用它，而不是启用完整的严格模式（第 17 行：noImplicitAny 仍设为 false，限制更宽松）：这是一种教学上的折中，既保留类型安全的精髓，又不要求为每个变量都添加类型注解。

    这一步使用大约十个 curl 场景，针对服务器的一个测试副本（内存数据库，预先填充了 admin/admin 和 user/user 两个账户）进行了验证：
